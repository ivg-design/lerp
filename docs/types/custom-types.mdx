# Lesson 2.2: Custom Types & Unions

## Learning Objectives
- Define custom type aliases with the `type` keyword
- Create table types (interfaces) for complex data
- Use union types for flexible values
- Understand and use optional types (`?`)
- Implement discriminated unions for state management

---

## AE/JS Syntax Comparison

If you're coming from After Effects expressions or JavaScript/TypeScript, here's how custom types compare:

| Concept | JavaScript/TypeScript | Luau (Rive) | Notes |
|---------|----------------------|-------------|-------|
| Type alias | `type Age = number` | `type Age = number` | Same syntax! |
| Object type | `{ name: string }` | `{ name: string }` | Same syntax! |
| Union type | `string \| number` | `string \| number` | Same syntax! |
| Optional property | `email?: string` | `email: string?` | `?` placement differs! |
| Literal union | `"up" \| "down"` | `"up" \| "down"` | Same syntax! |
| Read-only | `readonly x: number` | `read x: number` | Different keyword |
| Intersection | `A & B` | `A & B` | Same syntax! |

:::danger Critical Difference: Optional Syntax
```lua
-- TypeScript: ? comes BEFORE the colon
email?: string

-- Luau: ? comes AFTER the type name
email: string?
```
This is the most common source of confusion when coming from TypeScript!
:::

## Rive Context

In Rive scripts, your `export type` defines the shape of `self`. Custom types help keep complex Rive data (inputs, paths, runtime state) clean and safe.

**Why does this matter?** As your animations grow more complex, you need structured data. A character might have stats, inventory, and position. Custom types let you organize this cleanly.

Common Rive use cases for custom types:
- Nested state objects for complex animations
- Union types for state machine states
- Optional types for late-bound references
- Type aliases for domain-specific values (angles, pixels, etc.)

---

## Why Custom Types?

In Lesson 2.1, we used built-in types like `number` and `string`. But real applications need custom data structures:

- Player stats with multiple properties
- Configuration objects
- State machines with different states
- Data from ViewModels

Custom types give names to these structures, making code self-documenting and type-safe.

---

## Type Aliases

Type aliases give meaningful names to types:

```lua
-- Type alias (gives a name to a type)
type Age = number

-- Table type (defines shape of data)
type Player = {
    name: string,
    health: number,
}

-- Union type (can be one of several types)
type StringOrNumber = string | number

-- Optional type (can be nil)
type MaybeString = string?
```

**JavaScript/TypeScript Equivalent:**
```typescript
// TypeScript - almost identical!
type Age = number;

type Player = {
    name: string;
    health: number;
};

type StringOrNumber = string | number;

type MaybeString = string | null;  // null instead of nil
```

## Practice Exercises

### Exercise 1: Basic Type Aliases

**Goal:** Create meaningful names for primitive types to improve code readability.

**Why This Matters:** When you see `local width: Pixels = 1920`, it's immediately clear what the number represents. `local width: number = 1920` requires more context.

**Real-World Use:** In game development, you might have `type Damage = number`, `type Health = number`, `type Percentage = number`—all numbers, but with different meanings.

**Step-by-Step Setup:**
1. Create a new Node Script in Rive
2. Add `--!strict` at the top
3. Define type aliases before your `export type`
4. Use those aliases in variable declarations

**Rive setup:** Attach the script to any node and open the Console panel.

**Expected result:** The Console prints the screen size, progress, and color alias values.

**Task**: Create type aliases and use them in your code:

```lua
--!strict

-- Create these type aliases
type Pixels = number
type Percentage = number
type ColorHex = string

export type TypeAliasDemo = {}

function init(self: TypeAliasDemo): boolean
    -- Use your type aliases
    local screenWidth: Pixels = 1920
    local completion: Percentage = 75
    local background: ColorHex = "#FF5500"

    print(`Screen: {screenWidth}px`)
    print(`Progress: {completion}%`)
    print(`Color: {background}`)

    -- Type aliases are just names - this still works
    local anotherWidth: Pixels = 100 + 200  -- Pixels is just number

    return true
end

function draw(self: TypeAliasDemo, renderer: Renderer)
end

return function(): Node<TypeAliasDemo>
    return { init = init, draw = draw }
end
```

**Key insight**: Type aliases don't create new types—they're just names for existing types. A `Pixels` variable can accept any `number`. This is for documentation and clarity, not enforcement.

### Exercise 2: Table Types (Interfaces)

**Goal:** Define the shape of complex objects using table types.

**Why This Matters:** When you define a `type Enemy = { name: string, health: number, damage: number }`, you can't accidentally forget to include the `damage` property. The type checker enforces it.

**Real-World Use:** Every game entity (player, enemy, item, projectile) should have a defined type. This prevents bugs like "undefined is not an object" that plague JavaScript.

**Step-by-Step Setup:**
1. Create a new Node Script in Rive
2. Define table types using `type Name = { ... }`
3. Create variables that match those types
4. Try removing a required property to see the error

**Rive setup:** Attach the script to any node and open the Console panel.

**Expected result:** The Console prints the enemy, weapon, and spawn values; missing required properties trigger editor errors.

**Task**: Define and use table types:

```lua
--!strict

-- Define these types
type Enemy = {
    name: string,
    health: number,
    damage: number,
}

type Weapon = {
    name: string,
    power: number,
    range: number,
}

type Position = {
    x: number,
    y: number,
}

export type TableTypesDemo = {}

function init(self: TableTypesDemo): boolean
    -- Create instances matching your types
    local goblin: Enemy = {
        name = "Goblin",
        health = 30,
        damage = 5
    }

    local sword: Weapon = {
        name = "Iron Sword",
        power = 15,
        range = 2
    }

    local spawn: Position = {
        x = 100,
        y = 200
    }

    -- Types prevent errors - this would fail:
    -- local brokenEnemy: Enemy = { name = "Orc" }  -- Missing health and damage!

    print(`Enemy: {goblin.name} with {goblin.health} HP`)
    print(`Weapon: {sword.name} ({sword.power} damage)`)
    print(`Position: ({spawn.x}, {spawn.y})`)

    return true
end

function draw(self: TableTypesDemo, renderer: Renderer)
end

return function(): Node<TableTypesDemo>
    return { init = init, draw = draw }
end
```

**JavaScript/TypeScript Equivalent:**
```typescript
// TypeScript - nearly identical syntax
type Enemy = {
    name: string;
    health: number;
    damage: number;
};

const goblin: Enemy = {
    name: "Goblin",
    health: 30,
    damage: 5
};

// This would also error in TypeScript:
// const broken: Enemy = { name: "Orc" };  // Missing properties
```

### Exercise 3: Nested and Complex Types

**Goal:** Build sophisticated data structures by composing smaller types.

**Why This Matters:** Real applications have nested data. A character has stats, which have individual values. A game has players, which have inventories, which have items. Type composition keeps this manageable.

**Real-World Use:** RPG characters, UI component hierarchies, game configuration systems—all benefit from nested types.

**Step-by-Step Setup:**
1. Define small, focused types first
2. Compose them into larger types
3. Create factory functions that return properly typed objects

**Rive setup:** Attach the script to any node and open the Console panel.

**Expected result:** The Console prints the character's stats, inventory, and position based on the composed types.

**Task**: Build a character system with nested types:

```lua
--!strict

-- Define these types in order
type Stats = {
    strength: number,
    defense: number,
    speed: number,
}

type Inventory = {
    items: {string},
    gold: number,
}

type Position = { x: number, y: number }

type Character = {
    name: string,
    level: number,
    stats: Stats,
    inventory: Inventory,
    position: Position,
}

-- Function with typed parameter and return
local function createCharacter(name: string, level: number): Character
    return {
        name = name,
        level = level,
        stats = {
            strength = 10 + level * 2,
            defense = 5 + level,
            speed = 8 + level
        },
        inventory = {
            items = {"Starter Sword", "Health Potion"},
            gold = 100
        },
        position = {
            x = 0,
            y = 0
        }
    }
end

local function printCharacter(char: Character)
    print(`=== {char.name} (Level {char.level}) ===`)
    print(`STR: {char.stats.strength}, DEF: {char.stats.defense}, SPD: {char.stats.speed}`)
    print(`Gold: {char.inventory.gold}`)
    print(`Items: {#char.inventory.items}`)
    print(`Position: ({char.position.x}, {char.position.y})`)
end

export type NestedTypesDemo = {}

function init(self: NestedTypesDemo): boolean
    local hero = createCharacter("Aria", 5)
    printCharacter(hero)

    -- Modify nested properties
    hero.stats.strength += 5
    hero.inventory.gold -= 50
    table.insert(hero.inventory.items, "Magic Ring")

    print("\nAfter upgrades:")
    printCharacter(hero)

    return true
end

function draw(self: NestedTypesDemo, renderer: Renderer)
end

return function(): Node<NestedTypesDemo>
    return { init = init, draw = draw }
end
```

### Exercise 4: Union Types

**Goal:** Handle values that can be one of several different types.

**Why This Matters:** Sometimes a function needs to accept different types. An ID might be a number OR a string. A movement command might be coordinates OR a direction name. Union types handle this safely.

**Real-World Use:** API responses (success or error), form inputs (string or number), game commands (action or direction).

**Step-by-Step Setup:**
1. Define union types with the `|` operator
2. Use `type()` to check which type you have
3. Handle each case appropriately

**Rive setup:** Attach the script to any node and open the Console panel.

**Expected result:** The Console prints different output depending on whether each value is a number, string, or movement table.

**Task**: Work with union types:

```lua
--!strict

-- A value that could be a number or a string
type ID = number | string

-- A result that could be success (string) or error code (number)
type Result = string | number

-- A value that could be a position OR a direction name
type Movement = {x: number, y: number} | "up" | "down" | "left" | "right"

export type UnionDemo = {}

-- This function accepts either type
local function printID(id: ID)
    -- We need to check which type it is before using type-specific operations
    if type(id) == "number" then
        print(`Numeric ID: {id}`)
    else
        print(`String ID: {id}`)
    end
end

-- Process movement - could be coordinates or direction
local function processMovement(move: Movement)
    if type(move) == "string" then
        print(`Direction: {move}`)
    else
        print(`Coordinates: ({move.x}, {move.y})`)
    end
end

function init(self: UnionDemo): boolean
    printID(12345)
    printID("ABC-789")

    processMovement("up")
    processMovement("left")
    processMovement({x = 10, y = 20})

    return true
end

function draw(self: UnionDemo, renderer: Renderer)
end

return function(): Node<UnionDemo>
    return { init = init, draw = draw }
end
```

**Expected Output:**
```
Numeric ID: 12345
String ID: ABC-789
Direction: up
Direction: left
Coordinates: (10, 20)
```

**JavaScript/TypeScript Equivalent:**
```typescript
// TypeScript union types work the same way
type ID = number | string;

function printID(id: ID) {
    if (typeof id === "number") {
        console.log(`Numeric ID: ${id}`);
    } else {
        console.log(`String ID: ${id}`);
    }
}
```

### Exercise 5: Optional Types

**Goal:** Handle values that might not exist (can be nil).

**Why This Matters:** Not every user has an email. Not every character has a weapon equipped. Optional types let you express "this might be missing" in the type system.

**Real-World Use:** User profiles with optional fields, game inventories with empty slots, configuration with optional overrides.

**Step-by-Step Setup:**
1. Add `?` after a type to make it optional
2. Always check for nil before using the value
3. Use fallback values when appropriate

**Rive setup:** Attach the script to any node and open the Console panel.

**Expected result:** The Console prints different output depending on which optional fields are present.

**Task**: Handle optional values safely:

```lua
--!strict

type UserProfile = {
    username: string,
    displayName: string?,      -- Optional: might not be set
    email: string?,            -- Optional
    age: number?,              -- Optional
    verified: boolean,
}

-- This function REQUIRES an email
local function sendEmail(email: string, message: string)
    print(`Sending "{message}" to {email}`)
end

-- Get display name, fallback to username if not set
local function getDisplayName(user: UserProfile): string
    if user.displayName then
        return user.displayName
    else
        return user.username
    end
end

-- Safely send a welcome email (only if email exists)
local function sendWelcomeEmail(user: UserProfile)
    if user.email then
        sendEmail(user.email, "Welcome!")
    else
        print(`No email on file for {user.username}`)
    end
end

-- Get age category
local function getAgeCategory(user: UserProfile): string
    if user.age then
        if user.age < 18 then
            return "minor"
        else
            return "adult"
        end
    else
        return "unknown"
    end
end

export type OptionalDemo = {}

function init(self: OptionalDemo): boolean
    local user1: UserProfile = {
        username = "warrior42",
        displayName = "The Mighty Warrior",
        email = "warrior@example.com",
        age = 25,
        verified = true
    }

    local user2: UserProfile = {
        username = "newbie",
        verified = false
        -- No displayName, email, or age!
    }

    print(`User 1 display: {getDisplayName(user1)}`)
    print(`User 2 display: {getDisplayName(user2)}`)

    sendWelcomeEmail(user1)
    sendWelcomeEmail(user2)

    print(`User 1 category: {getAgeCategory(user1)}`)
    print(`User 2 category: {getAgeCategory(user2)}`)

    return true
end

function draw(self: OptionalDemo, renderer: Renderer)
end

return function(): Node<OptionalDemo>
    return { init = init, draw = draw }
end
```

**Expected Output:**
```
User 1 display: The Mighty Warrior
User 2 display: newbie
Sending "Welcome!" to warrior@example.com
No email on file for newbie
User 1 category: adult
User 2 category: unknown
```

:::danger Always Check Optionals
```lua
-- WRONG: email might be nil!
sendEmail(user.email)  -- Type error: string? is not string

-- CORRECT: Check first
if user.email then
    sendEmail(user.email)  -- Now Luau knows it's string
end
```
:::

### Exercise 6: Discriminated Unions (State Machines)

**Goal:** Use a "kind" field to distinguish between different states in a union.

**Why This Matters:** State machines are everywhere—loading states, game states, animation states. Discriminated unions let you model these safely, with the type system ensuring you handle all cases.

**Real-World Use:** Network request states (loading/success/error), character states (idle/walking/attacking), UI states (collapsed/expanded).

**Step-by-Step Setup:**
1. Define each state as a separate type with a `kind` field
2. Create a union of all states
3. Check `kind` to determine which state you're in
4. Luau automatically narrows the type based on the `kind` check

**Rive setup:** Attach the script to any node and open the Console panel.

**Expected result:** The Console prints state transitions with messages for idle, fetching, success, and error.

**Context**: A powerful pattern for state machines. Add a `kind` field to distinguish between states.

```lua
--!strict

-- Each state has a "kind" field that identifies it
type LoadingState = { kind: "idle" }
type FetchingState = { kind: "fetching", url: string, progress: number }
type SuccessState = { kind: "success", data: string }
type ErrorState = { kind: "error", message: string, code: number }

-- Union of all states
type AppState = LoadingState | FetchingState | SuccessState | ErrorState

local function renderState(state: AppState)
    -- Luau narrows the type based on the kind field
    if state.kind == "idle" then
        print("Ready to load...")
    elseif state.kind == "fetching" then
        -- Inside this block, state is known to be FetchingState
        print(`Loading {state.url}: {state.progress}%`)
    elseif state.kind == "success" then
        print(`Loaded: {state.data}`)
    elseif state.kind == "error" then
        print(`Error {state.code}: {state.message}`)
    end
end

-- State transition functions
local function startLoading(url: string): FetchingState
    return { kind = "fetching", url = url, progress = 0 }
end

local function updateProgress(state: FetchingState, newProgress: number): FetchingState
    return { kind = "fetching", url = state.url, progress = newProgress }
end

local function finishLoading(data: string): SuccessState
    return { kind = "success", data = data }
end

local function failLoading(message: string, code: number): ErrorState
    return { kind = "error", message = message, code = code }
end

export type StateDemo = {
    currentState: AppState,
}

function init(self: StateDemo): boolean
    -- Simulate a loading sequence
    self.currentState = { kind = "idle" }
    renderState(self.currentState)

    self.currentState = startLoading("https://api.example.com/data")
    renderState(self.currentState)

    -- Type guard: only update progress if we're in fetching state
    if self.currentState.kind == "fetching" then
        self.currentState = updateProgress(self.currentState, 50)
        renderState(self.currentState)

        self.currentState = updateProgress(self.currentState, 100)
        renderState(self.currentState)
    end

    -- Success path
    self.currentState = finishLoading("Player data loaded!")
    renderState(self.currentState)

    -- Alternative: Error path
    print("\n--- Simulating error ---")
    self.currentState = { kind = "idle" }
    self.currentState = startLoading("https://api.example.com/missing")
    self.currentState = failLoading("Resource not found", 404)
    renderState(self.currentState)

    return true
end

function draw(self: StateDemo, renderer: Renderer)
end

return function(): Node<StateDemo>
    return {
        init = init,
        draw = draw,
        currentState = { kind = "idle" }
    }
end
```

**JavaScript/TypeScript Equivalent:**
```typescript
// This pattern is identical in TypeScript!
type LoadingState = { kind: "idle" };
type FetchingState = { kind: "fetching"; url: string; progress: number };
type SuccessState = { kind: "success"; data: string };
type ErrorState = { kind: "error"; message: string; code: number };

type AppState = LoadingState | FetchingState | SuccessState | ErrorState;

function renderState(state: AppState) {
    switch (state.kind) {
        case "idle":
            console.log("Ready to load...");
            break;
        case "fetching":
            // TypeScript knows state.url and state.progress exist here
            console.log(`Loading ${state.url}: ${state.progress}%`);
            break;
        // ... etc
    }
}
```

### Exercise 7: Read-Only Properties

**Goal:** Prevent modification of certain properties after initialization.

**Why This Matters:** Some values should never change—configuration constants, version numbers, IDs. Read-only properties enforce this at the type level.

**Real-World Use:** Game configuration, entity IDs, immutable settings.

**Rive setup:** Attach the script to any node and open the Console panel.

**Expected result:** The Console prints config values; attempts to mutate read-only fields should be flagged by the editor.

**Task**: Prevent modification of certain properties:

```lua
--!strict

-- Read-only properties use the 'read' modifier
type ImmutableConfig = {
    read version: string,
    read maxPlayers: number,
    read debug: boolean,
}

type MutableConfig = {
    currentPlayers: number,
    serverName: string,
}

type GameConfig = ImmutableConfig & MutableConfig

export type ReadOnlyDemo = {}

function init(self: ReadOnlyDemo): boolean
    local config: GameConfig = {
        version = "1.0.0",
        maxPlayers = 100,
        debug = false,
        currentPlayers = 0,
        serverName = "Main Server"
    }

    -- Reading is always OK
    print(`Version: {config.version}`)
    print(`Max Players: {config.maxPlayers}`)

    -- Mutable properties can be changed
    config.currentPlayers = 42
    config.serverName = "Updated Server"

    -- These would error:
    -- config.version = "2.0.0"  -- Error: cannot write to read-only property
    -- config.maxPlayers = 200   -- Error: cannot write to read-only property

    print(`Current Players: {config.currentPlayers}`)
    print(`Server: {config.serverName}`)

    return true
end

function draw(self: ReadOnlyDemo, renderer: Renderer)
end

return function(): Node<ReadOnlyDemo>
    return { init = init, draw = draw }
end
```

**JavaScript/TypeScript Equivalent:**
```typescript
// TypeScript uses 'readonly' instead of 'read'
type ImmutableConfig = {
    readonly version: string;
    readonly maxPlayers: number;
    readonly debug: boolean;
};
```

## Common Mistakes

:::danger Avoid These Errors

1. **Forgetting required properties**: Table types require ALL non-optional properties
   ```lua
   type Enemy = { name: string, health: number }

   -- WRONG: Missing health
   local enemy: Enemy = { name = "Goblin" }

   -- CORRECT: All properties provided
   local enemy: Enemy = { name = "Goblin", health = 30 }
   ```

2. **Not checking optionals**: Always guard `string?` before use
   ```lua
   -- WRONG: email might be nil
   print(user.email:upper())

   -- CORRECT: Check first
   if user.email then
       print(user.email:upper())
   end
   ```

3. **Accessing union properties without narrowing**: Check the type first
   ```lua
   type Result = {success: true, data: string} | {success: false, error: string}

   -- WRONG: Don't know which type yet
   print(result.data)

   -- CORRECT: Check first
   if result.success then
       print(result.data)  -- Luau knows data exists
   end
   ```

4. **Confusing `?` and `| nil`**: They're equivalent, but `?` is cleaner
   ```lua
   -- Both mean the same thing
   email: string?
   email: string | nil
   ```

:::
